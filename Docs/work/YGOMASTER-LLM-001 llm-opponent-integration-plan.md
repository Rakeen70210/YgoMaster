# YGOMASTER-LLM-001: LLM opponent integration plan

## Context

The shared discussion ([ChatGPT share](https://chatgpt.com/share/6a42778c-b888-83e8-be88-701e80455612)) analyzed how to modify YgoMaster/Master Duel so an LLM such as DeepSeek can control an opponent.

The durable conclusion is: **build an LLM opponent as a thin YgoMaster adapter plus an external local broker, not by rewriting Konami's CPU AI or writing directly into native memory offsets.**

Confirmed local code anchors in the current checkout:

- `YgoMasterClient/DuelDll.cs`: duel tick and command commit surface, including `DLL_DuelSysAct`, `DLL_DuelComMovePhase`, `DLL_DuelComDoCommand`, and `ActionsToRunInNextSysAct`.
- `YgoMasterClient/DuelDll.ProxyFunctions.cs`: hooked `duel.dll` query helpers for command masks, phases, dialogs, list selections, attack masks, card IDs, unique IDs, phase, step, and turn.
- `YgoMasterServer/Pvp.cs`: existing capture/replay of many duel engine values, including command masks, list/dialog data, card state, phase/turn values, and `RunEffectSeq` validation.
- `YgoMasterServer/Sim/DuelSimulator*.cs` and `YgoMasterServer/Sim/CpuContest.cs`: likely harnesses for offline evaluation before touching the UI path.
- `Docs/LiveMods.md`: live modding risk boundary; custom PvE duels are no-reward and are the correct target environment.

## Plan

1. **Prove observability first.**
   Add logging around existing duel decision windows before any LLM call. Capture `RunEffectSeq`, view/choice context, command masks, phase masks, dialog/list prompts, visible card IDs, selected manual action, and final committed action.

2. **Define a legal-action schema.**
   Convert existing query surfaces into a compact `legal_actions` list. Initial action types should be `move_phase`, `command`, `dialog_result`, `list_select`, and `cancel`.

3. **Build a loopback broker.**
   Run a local service on `127.0.0.1` that owns API keys, prompt construction, timeout policy, provider calls, and audit logs. The game process should only serialize public state, send a request, receive one JSON action, and schedule a validated commit.

4. **Start with one narrow commit path.**
   Prototype only "choose a card command or move phase" before handling full dialog/list complexity. Commit through existing functions such as `DLL_DuelComDoCommand` and `DLL_DuelComMovePhase`.

5. **Add strict validation.**
   The response must choose an existing `action_id`. Before commit, rebuild the current legal-action list, reject stale `RunEffectSeq`, reject missing/changed action IDs, and fall back on timeout or invalid output.

6. **Integrate DeepSeek through the broker only.**
   Use strict JSON output or tool-calling behind the broker. As of 2026-06-29, DeepSeek docs list `deepseek-v4-pro` and `deepseek-v4-flash`; older `deepseek-chat` and `deepseek-reasoner` names are scheduled for deprecation on 2026-07-24.

7. **Validate offline/private only.**
   Keep this in custom PvE/private testing. Add a hard config gate so the LLM controller cannot run in live/ranked contexts.

8. **Measure before adding strategy.**
   Track action validity rate, stale-action rejection rate, timeout rate, decision latency p50/p95, token size, cost per duel, duel completion rate, and hidden-information leakage.

## Decisions

- **Use adapter + external broker.**
  **Why:** Keeps secrets, network code, retries, logging, and model dependencies outside the game process while leaving the in-game patch small.

- **The LLM chooses from legal actions only.**
  **Why:** YgoMaster/`duel.dll` should remain the source of legality. The LLM should never infer legality from card text, screenshots, or raw memory.

- **Use `ActionsToRunInNextSysAct` for game-side commit scheduling.**
  **Why:** The code already marks it as the correct duel-thread queue. Arbitrary background mutation would be brittle.

- **Avoid memory-offset hijacking for the first implementation.**
  **Why:** The shared analysis contained speculative claims about memory offsets and native writes. Existing C# hook/proxy surfaces are safer and easier to validate.

- **Start with manual-play instrumentation and a mock broker.**
  **Why:** The first risk is not model quality. The first risk is whether every decision window and commit path can be observed, serialized, and replayed reliably.

- **Make first runtime logging neutral, not opponent-only.**
  **Why:** In PvP, either player can be the acting side depending on the client and turn. Logging all `WaitInput` windows with explicit `acting_player` keeps the corpus symmetric and avoids hard-coding the future actor assignment.

- **Limit the first broker control path to the non-local PvP player.**
  **Why:** Letting the broker control `Duel.MyID` would leave the human UI active and risks double-committing. Opponent/non-local control matches the current `CpuThinking` replacement path and is the safer first integration target.

- **Expose `list_index` only for strict single-select windows.**
  **Why:** The current commit primitive is one `DLL_DuelListSetIndex` call. Multi-select, optional-pick, or pick-N windows need a separate validated flow before the broker should control them.

- **Defer cancel/skip actions.**
  **Why:** The codebase has low-level cancel calls, but there is not yet a grounded current-state legality surface equivalent to command masks, enabled dialog items, or single-select list metadata.

- **Keep schema-v2 `public_state` public-only.**
  **Why:** The current runtime has not validated `DLL_DuelGetHandCardOpen` or `DLL_DuelGetCardFace` semantics. Closed hand identities, acting-player private hand knowledge, face-down field identities, and banished/field identities stay out of provider payloads until real duel logs prove the visibility rules.

- **Provider failures should be explicit, not silent deterministic choices.**
  **Why:** If the configured model, endpoint, or provider response is broken, silently committing the mock deterministic fallback would hide the failure and make the duel look LLM-controlled when it is not. Broker-side `provider_error` lets the game fall back through the existing CPU path.

- **Keep direct API as the stable provider path; treat CLI providers as experimental.**
  **Why:** `grok_cli` and `opencode_cli` can exercise subscription/OAuth-backed local tools, but they add subprocess startup, auth/session, output-format, and latency risks. They are optional adapters behind the broker, not the default validation path.

- **Keep the net8 harness as a local verification runner, not the game target.**
  **Why:** The game/client projects still target .NET Framework 4.8. The net8 harness exists only to execute the same LLM source tests on Linux where a .NET Framework runtime is not available.

- **Use JSONL lifecycle events plus a threshold analyzer for longer-duel validation.**
  **Why:** Long manual duels are too noisy to validate by eyeballing `LlmDecisionLog.jsonl`. Structured request/response/skip/reject/commit events plus `Tools/analyze_llm_duel_log.py` make it clear whether the broker was actually invoked, whether it responded, what action type committed, and whether a run covered enough turns/action types.

## Validation

Minimum validation gates:

- Logging-only build captures manual decisions without changing duel behavior.
- Mock broker can choose a deterministic legal action and commit it through the existing duel functions.
- Invalid or stale `action_id` responses are rejected.
- Broker timeout falls back without freezing the duel.
- Prompt audit confirms no hidden opponent hand, face-down identity, or future deck order is serialized.
- LLM-backed run completes at least one controlled private PvP duel. The current broker-control slice does not exercise through solo/PvE CPU duels.
- Metrics are recorded per decision: latency, token count, selected action, validation result, and commit result.

## Operational gotchas

- Do not put remote API keys in game/plugin config. Store them only in the broker environment or OS secret storage.
- Do not make direct remote API calls from the hook layer; network failures should not destabilize Unity/IL2CPP or the duel thread.
- Do not treat `curl` or non-interactive launch calls as full game validation. For this checkout, validate runtime behavior through actual logs/processes/listeners and in-game behavior.
- Do not use hidden game-state access just because the mod can read it. The broker prompt must follow a public-only visibility policy.
- Broker-side `provider_error` is now preserved when the broker returns a structured non-2xx JSON envelope; connection failures where the broker is never reached still surface as `transport_error`.
- Plain `dotnet build` uses the project default output paths and can overwrite the live runtime executables under the checkout. For local verification on this runtime checkout, redirect output with `-p:OutputPath=/tmp/ygomaster-build/...`.
- Use `Tools/prepare_llm_runtime.py` for private-duel validation prep instead of manually copying EXEs or hand-editing both settings files. Combined settings+binary writes are preflighted and roll back on later write failure, but binary deploy write still must wait until the game is fully closed.
- Use `Tools/prepare_llm_runtime.py --status` as the runtime validation dashboard: before deploy, active `game_processes` and `matches_build=false` are blockers; after launch, `broker.health.ok=true` proves the expected local broker identity, and `broker.ready_for_llm_validation=true` is required for real provider-backed validation. `broker.listening=true` alone only proves some TCP listener is present.
- The ignored runtime `Data/ClientData/ClientSettings.json` may intentionally differ from the tracked source settings during validation. As of 2026-06-29, the runtime copy is enabled for LLM validation while the tracked source copy remains default-off.
- A healthy broker with `provider_configured=false` proves only deterministic fallback plumbing. Real LLM validation requires selecting a configured provider and confirming `broker.ready_for_llm_validation=true`; for DeepSeek this means `YGO_LLM_BROKER_PROVIDER=deepseek_api` plus `YGO_LLM_BROKER_API_KEY`, with optional base URL/model overrides.
- Keep `YGO_LLM_BROKER_PROVIDER_TIMEOUT` below `LlmBrokerTimeoutMs`; for hosted models, raise both values together rather than only increasing the broker-side provider timeout.
- For `grok_cli` or `opencode_cli`, the local CLI must already be logged in/authenticated and the game timeout should be raised with `Tools/prepare_llm_runtime.py --settings --timeout-ms ...`; keep `YGO_LLM_BROKER_CLI_TIMEOUT` slightly below the game timeout.
- The current broker-control path is private PvP only and controls the non-local player. A solo/PvE duel against the built-in CPU does not exercise the LLM broker path.
- Older `LlmDecisionLog.jsonl` files from before the lifecycle-audit slice can still be summarized for `decision_window` and `llm_broker_committed` coverage, but they will not contain `llm_broker_request_started`, `llm_broker_response`, `llm_broker_rejected`, or `llm_broker_commit_skipped`. Fresh lifecycle coverage requires redeploying the rebuilt client and starting a new duel.
- If the direct `../YgoMasterP2` Proton launch exits immediately with an empty log, use `Tools/launch_p2_client.sh`. The working path sets `STEAM_COMPAT_APP_ID=1449850`, `SteamAppId=1449850`, and `SteamGameId=1449850`; process checks are still the source of truth.
- After live room-duel tests, closing the visible windows may still leave Proton/MonoRun root client/server, P2 client, or spawned `--pvp` server processes alive. Verify with a process check before assuming a deploy-safe closed state.
- With slow CLI providers, the remote P2 client can advance automatic/simple player-1 windows before the root broker response returns. Treat `llm_broker_response` followed by `llm_broker_rejected: stale_run_effect_seq` as a provider-latency/remote-client race unless the root log shows root sent the player-1 command.
- Proton 10.0 currently fails even for unmodded `masterduel.exe` in this prefix with `coremessaging.dll.DllGetActivationFactory`. GE-Proton10-34 is the working runtime as of 2026-06-30; a temporary prefix backup exists at `/tmp/compatdata-1449850-before-ge-test-20260630-0938/`.
- With GE-Proton10-34, starting `YgoMaster.exe` before `YgoMasterClient.exe` can leave the client Proton process stuck before `MonoRun.exe` starts. The working launcher order is client first, then delayed server and forwarder startup.
- Launch recovery intentionally rolled the root runtime EXEs back to older pre-LLM binaries and disabled runtime `LlmBrokerEnabled`. Re-deploy the LLM runtime only after baseline Steam launch remains stable.
- Keep this out of live/ranked play. YgoMaster live-mod docs explicitly warn that live modding risks bans, and custom PvE no-reward mode is the appropriate target.
